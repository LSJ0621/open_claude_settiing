# Claude Code 운영 설정

에이전트를 어떻게 운영하는지 정한 규칙(CLAUDE.md)과, 규칙으로는 막을 수 없어 hook으로 막은 것 하나를 공개합니다.

## 왜 이렇게 만들었나

### 메인 세션의 컨텍스트는 맥락을 담는 곳이다

에이전트는 대화 없이는 내 상황, 목적, 암묵지를 모릅니다. 그래서 작업 전에 상황 설명과 도메인 이야기를 먼저 넣어 맥락을 채웁니다. 그렇게 채운 맥락은 비쌉니다. 코드 읽기나 조사로 컨텍스트가 차면 맥락이 밀려나고, 경험상 1M 컨텍스트 기준 60%를 넘으면 할루시네이션이 심해졌습니다.

그래서 메인 세션은 결정만 하고, 파일 읽기·코드 작성·조사는 fork와 서브에이전트에 시켜 결과만 받습니다. 메인에는 맥락과 결정만 남습니다. 그래도 넘칠 때가 있으니 컨텍스트가 많이 찼다 싶으면 맥락과 의사결정 기록을 핸드오프 문서로 빼서 새 세션이 이어받게 합니다.

### 우선순위

1. 정확도
2. 속도
3. 토큰 사용량

위임 구조는 정확도를 위한 것이고, 병렬 규칙은 속도를 위한 것입니다. 토큰은 마지막이라, 정확도를 위해서라면 fork를 여러 번 띄우는 비용을 감수합니다.

### 지침과 hook의 경계

CLAUDE.md는 에이전트가 읽고 따르는 지침입니다. 안 따를 수도 있습니다. 어기면 되돌릴 수 없는 것만 hook으로 막습니다. 비밀값 파일 접근이 그것입니다. 지침에도 "읽지 마라"가 있지만, 도구 실행 전에 경로와 명령을 검사해 거부하는 hook을 겹쳤습니다. `settings.hooks.example.json`이 그 부분입니다.

### 테스트는 회귀 방지가 목적

기능을 추가하거나 로직을 고칠 때 다른 기능이 망가지지 않게 하는 게 주된 이유입니다. 도메인 로직은 테스트 먼저, 버그는 실패하는 테스트로 재현한 뒤 고칩니다. 100% 커버리지는 목표가 아닙니다.

### 응답 양식은 빠른 판단을 위한 것

응답이 이해하기 어려우면 판단이 늦어집니다. 핵심만, 사실 위주로, 짧게 쓰게 했습니다. 계획 문서에서 파일명이나 변수명은 어차피 코드를 열어보지 않으니 필요 없습니다. 어떤 식으로 할 건지 맥락만 정확히 파악하면 됩니다.

## 스킬은 어떻게 만드나

두 갈래입니다.

- 내 성향이 들어가는 것은 직접 만듭니다. 응답 양식처럼 내가 읽기 편한 형태는 남이 대신 정할 수 없습니다. 대화하면서 좋았던 양식을 기록으로 쌓고, 패턴이 보이면 스킬로 굳힙니다.
- 전문성이 필요한 것은 가져다 씁니다. 디자인은 내가 디자이너가 아니니, 디자이너가 만든 스킬을 설치하는 게 결과가 낫습니다.

기준은 하나입니다. 이 지식이 내 고유한 것인가, 남이 더 잘 아는 것인가.

## 배운 것

테스트를 에이전트로 대량 생성했다가 검토 없이 커버리지만 올린 적이 있습니다. 테스트는 코드가 어떻게 동작해야 하는지를 정해두고, 로직을 바꿀 때 망가진 게 없는지 확인하는 기준이라는 걸 그 뒤에 알았습니다. 지금은 핵심 도메인 로직, 경계값과 예외, 버그가 났던 지점에 집중해서 작성하고, 생성된 테스트는 무엇을 검증하는지 확인한 뒤 남깁니다.

## 파일

- `CLAUDE.md`: 전역 지침 원문
- `settings.hooks.example.json`: 비밀값 파일 접근을 차단하는 hook 발췌. hook 스크립트가 `jq`를 쓰므로 설치가 필요합니다.
